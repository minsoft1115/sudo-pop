코어 설계

sudo-pop 아키텍처

Hyprland/Wayland에서 sudo 비밀번호를 GUI 팝업으로 받으면서, pacman·vim 같은 대화형 명령의 터미널을 온전히 보존하는 단일 Rust 바이너리.

사양 plan.md 근거 rationale.md Hyprland 0.56.2 sudo 1.9.17p2
01

두 채널은 절대 교차하지 않는다

전체 설계가 이 그림 하나에서 나온다. sudo -A는 비밀번호 수집을 별도 프로세스로 격리하고 그 프로세스의 stdout만 익명 파이프로 가로챈다. 터미널의 fd 3종은 sudo가 손대지 않은 채 명령에게 그대로 넘어간다.

터미널 채널 — 명령이 쓰는 fd 비밀번호 채널 — 익명 파이프 
# sudo 가 askpass 를 호출하는 규약 (실측)
argv[1]  [sudo] password for <user>:   ← 프롬프트. 인자는 이것 하나뿐
fd 0     socket:[…]
fd 1     pipe:[…]                   ← 여기 쓴 첫 줄이 비밀번호
fd 2     상속됨                       ← 로그·경고는 여기로
02

단일 바이너리, 세 모드

askpass 모드는 사람이 직접 부르지 않는다. sudo가 심볼릭 링크를 통해 호출한다. SUDO_ASKPASS에는 인자를 붙일 수 없어(sudo가 값을 경로 그대로 exec한다) 링크 이름 자체가 모드 신호가 된다. 

$XDG_RUNTIME_DIR/sudo-pop/askpass  →(symlink)→  /usr/bin/sudo-pop

/run/user/1000  tmpfs  mode=700, uid=1000     소유자만 접근
심볼릭 링크는 exec 권한을 타깃에서 평가 → noexec 마운트 무관
tmpfs → 정리 불필요 → 래퍼가 exec() 를 쓸 수 있게 됨
03

래퍼 모드 — 다섯 개의 폴백 관문

하나라도 걸리면 GUI를 포기하고 평범한 sudo로 넘어간다. GUI를 못 띄우는 것이 sudo 자체를 못 쓰는 것보다 낫다는 원칙이다.

spawn 이 아니라 exec

프로세스를 통째로 대체하면 종료 코드 전파(시그널 사망 128+N 포함), SIGINT 전달, 프로세스 그룹, 잡 컨트롤(sudo pacman 중 Ctrl-Z), TTY 소유권이 전부 자동으로 해결된다.

캐시 프리체크는 두지 않는다. sudo -A는 실제로 비밀번호가 필요할 때만 askpass를 호출하므로 팝업 여부의 판단이 이미 sudo 안에 있다. 밖에서 sudo -n true로 미리 확인해 봐야 동작은 그대로이고, 캐시만 볼 뿐 명령별 NOPASSWD 규칙은 판정하지 못한다.

04

askpass 모드 — 순서가 곧 방어선

하드닝은 비밀번호가 메모리에 들어오기 전, GUI 초기화 이전에 끝나야 한다. 그리고 종료 분기에서 실패 경로는 반드시 무출력이어야 한다 — 개행 하나가 1건과 10건을 가른다.

panic = "abort" 는 하드닝과 세트

abort는 SIGABRT를 내고, 하드닝이 없으면 systemd-coredump가 비밀번호를 담은 메모리 전체를 디스크에 기록한다. 반대로 하드닝이 있으면 unwind가 잡지 못하는 GPU 드라이버발 SIGSEGV까지 함께 막히므로 abort가 더 안전하다. 두 설정은 항상 함께 다룬다.

05

모듈 구성

src/
├── main.rs              모드 판별 및 디스패치
├── init.rs              --init / --uninit
├── wrapper.rs           폴백 판정, 심볼릭 링크, exec
├── sudo_args.rs         sudo 옵션 스캐너 (래퍼·askpass 공용)
├── askpass/
│   ├── mod.rs           하드닝 → GUI → 출력 오케스트레이션
│   ├── harden.rs        PR_SET_DUMPABLE / RLIMIT_CORE
│   ├── secret.rs        zeroize 버퍼(+mlock), stdout 격리, raw write
│   ├── theme.rs         Omarchy 팔레트 → egui Visuals
│   ├── font.rs          fc-match → egui FontDefinitions
│   ├── invocation.rs    /proc/<ppid>/cmdline → 실행될 명령
│   └── gui.rs           eframe 창 — 독립 모듈로 격리
├── attempts.rs          재시도 가드 + faillock 조회
└── paths.rs             XDG_RUNTIME_DIR, 설정 경로 규약

gui.rs를 격리해 두는 이유는 wlr-layer-shell 오버레이로 옮길 가능성 때문이다. 그쪽은 윈도우 룰 의존이 0이고 키보드 그랩이 프로토콜 차원에서 보장되지만 구현 난도가 올라간다. 1단계는 eframe으로 완성하고, 룰 의존이 실제 문제를 일으킬 때 옮긴다.
